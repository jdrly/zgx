How this was measured

  • Machine: Apple M5 Max (Mac17,6, 18 cores, 128 GB), macOS 26.4 (25E246), AC Power.
  • Displays: 2 × Studio Display XDR (3200 x 1800 @ 120.00Hz); the window on the main display, nothing covering it.
  • Builds: every framework with its dist profile (release, fat LTO, one codegen unit) and the system allocator; rustc 1.96.0 (ac68faa20 2026-05-25). zgx at 282bfc0.
  • Trials: each a fresh launch of 20 s, the first 5 s discarded, the next 15 s sampled every 50 ms; 3 trials of each active mode, 5 of idle, sampled 20–35 s after launch. Medians are shown, the trials' range beside them. Frame timing is 8 separate 8 s captures per mode.
  • CPU: the app process's CPU time over the sample, as a percentage of one core (it can exceed 100).
  • GPU work: GPU cycles the app's process used per second, from the GPU's counters.
  • Frame time: the 99th percentile of the intervals between frames shown on screen; at 60 updates a second, 16.7 ms is on time (8.3 ms for the animation, drawn at 120 Hz). Long frames are intervals over 25 ms.
  • Memory: the process's physical footprint (what Activity Monitor shows: resident memory plus GPU memory it owns), averaged over the sample.

Caveats

  • Idle memory is two-level: an idle window settles at one of two levels about 25 MB apart, launch to launch, as the Metal driver returns its startup memory. Which level a launch lands on is the driver's timing, not the app's, so read idle memory with its range.
  • In the text-and-list scene, zgx's memory ties GPUI Fast's in the active modes.
  • The window server's own CPU, which drawing to the screen adds, is level for all three frameworks; it is in the data, not charted.
  • Binary size is not compared.
  • One machine, one session per scene; a personal Mac in use, other applications kept running (each run waited until the machine was quiet). Windows and Linux are not compared here.
